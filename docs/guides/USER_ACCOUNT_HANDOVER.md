# User account handover

In **Admin > Users**, open the account's password reset action (or **Change email & reset password** in Edit). Enter the real destination email and confirm. Leave the same email for an ordinary reset. The account UUID, role, permissions, hierarchy and business records are preserved; no new account is created.

The action requires the existing user-management permission, sensitive PIN and target-role authorization. Super Admin accounts (including the profile-level protection flag) cannot be reset through this action. The ordinary profile editor cannot change email.

The server first persists the password-change restriction, then revokes all existing application sessions and biometric credentials for that account, and only then updates Auth email and password together. A second revocation sweep follows the Auth update before credentials are disclosed. Login also rechecks credentials after creating its application session to close concurrent-login gaps. A supplied email is normalized and confirmed using the existing admin onboarding model. Check the destination carefully: there is no separate email ownership verification. The fresh temporary password is sent only to the resulting destination, never the old address.

The confirmation distinguishes successful delivery from delivery failure. If delivery fails after credentials change, use the privileged temporary-password display and share it securely, or repeat the action to generate a new password. Passwords must not be copied into logs, support tickets or this guide. Self-reset signs out the administrator; retain the temporary password before closing the result and signing in again.

## Credential serialization

Reset and permanent-password completion share an account-scoped PostgreSQL advisory transaction lock, including across server instances. A dedicated `pg.Client` holds an explicit transaction through fresh authorization, current-password verification (for completion), Auth updates, restriction changes, revocation sweeps and reset email delivery/response preparation. Concurrent requests for that account fail fast with HTTP 409 (`CREDENTIAL_CHANGE_BUSY`) and make no credential, restriction, revocation or email changes. Retry after the other operation finishes. The routes revalidate the live session/actor, PIN and target permission as applicable inside the lock; an initial session lookup cannot authorize stale completion after a reset. Renewed session cookies are carried into subsequent validation within the same request, so session-secret rotation does not invalidate that recheck.

The server requires `POSTGRES_URL_NON_POOLING` (preferred) or `POSTGRES_URL`. The transaction pins the backend even through a transaction pooler. Connection and SQL timeouts are five seconds; idle-in-transaction expiry is disabled locally while external Auth/email work is awaited. Connection loss blocks subsequent mutation steps and returns a generic unavailable error, never a local-mutex fallback. Hosted connections follow the existing server TLS configuration; plaintext is allowed only for `FFTS_DATA_ENVIRONMENT=development` after the existing development-target guard verifies the destination. Missing or invalid configuration fails closed with HTTP 503 (`CREDENTIAL_CHANGE_UNAVAILABLE`). No migration or additional table is required for this lock.

The lock coordinates these two application routes, not unrelated external Auth administrators. A lost database connection cannot undo an external Auth/email request already in flight; the response preserves confirmed/uncertain partial state instead of claiming rollback. Real database/pooler and browser runtime verification remain separate from mocked tests.

## Failure and retry

A failed restriction or revocation step does not send or disclose new credentials. If the final revocation sweep fails, Auth credentials have already changed; the partial state says so and the combined action must be retried to generate a fresh temporary password. The response identifies the failed stage and confirmed partial state. Applied restrictions and revocations are deliberately not rolled back. Retry the same combined action after correcting the failure. If Auth rejects a duplicate email, credentials remain unchanged but the password-change requirement and revocations have already been applied; correct the destination and retry. An unconfirmed Auth response is reported as potentially changed, not success. If self-reset revoked your session before a later failure, sign in again or ask another authorized administrator to retry.

The recipient signs in with the temporary password and must choose a different permanent password meeting the existing strength policy (8 characters, uppercase, lowercase and number). The server verifies the current password and clears the restriction only after confirming the Auth password change. An uncertain Auth response keeps the restriction and explicitly advises trying the new password before retrying. If clearing the flag fails, the new password is already active: use it as the current password on retry. After confirmed password completion, the page awaits the existing AuthProvider session refresh and verifies the same authenticated account with its restriction explicitly cleared before navigating. If refresh fails, the password is already changed: use **Retry refreshing access** or sign in with the new password. That recovery does not submit another password update. Pending accounts may inspect their auth session, bootstrap, change password or log out, but business authorization and fresh Supabase data tokens are denied. Biometric sign-in cannot bypass this step; re-enrol devices after completion.

## Existing direct-token limitation

Revocation of `app_auth_sessions` is **not immediate revocation of already-issued Supabase bearer JWTs**. These tokens have a 3600-second lifetime and current RLS is not bound to live custom sessions or the password-change flag. Existing direct tokens can remain usable until expiry, including after a reset or password replacement. Live server checks prevent new tokens and ordinary server authorization while pending; the browser discards its cached token when it observes the restricted session. This feature does not redesign RLS, widen permissions, or claim instant bearer-token invalidation. Launch assessment of that residual window remains separate.

The focused, mocked suite is `node node_modules/vitest/vitest.mjs run --config vitest.account-handover.config.ts --maxWorkers=1 --no-file-parallelism`. Its configuration disables env-file loading, explicitly selects one project and uses `tests/setup.ts` to strip database credentials and block real clients/network. Do not enable development integration for this suite. The companion static check is `node node_modules/typescript/bin/tsc --noEmit --incremental false`. Neither check sends real mail or mutates a database.

## Database permissions and deployment order

`supabase/migrations/20261109190808_staff_account_handover_guards.sql` makes profile identity, authority and onboarding fields server-owned. Browser roles cannot insert/delete profiles, assign roles or managers, or clear `must_change_password`. New Auth accounts start unprivileged regardless of user metadata; checked admin provisioning assigns the authorised role afterwards. Existing contact-field updates remain available, and direct holiday-allowance updates retain the existing absence-permission check. No business records are rewritten by this migration.

Deploy the compatible reset/password-completion routes before applying these grants to an existing hosted database. Take the current function/ACL inventory and check unchanged data fingerprints. For future rollback, assess both the app and permission migration together; older application code may expect authenticated access to the now-protected flag.

The NAS-only real PostgreSQL regression is `node scripts/testing/verify-account-handover-guards.cjs`. It validates the exact development target and running app, creates fictional fixtures and replays the migration inside a transaction, then rolls everything back. See `scripts/README.md`.

Hosted public sign-up and leaked-password protection are separate Supabase Auth settings. Keep staff provisioning admin-controlled by disabling public sign-up, and enable leaked-password protection before launch. The current connector cannot update those settings; their completion must be verified in the Supabase dashboard.
